# 多画质批次设计方案

> 实现状态：已按本文方案完成（2026-08-20）。后端 schema v2、原子画质计划、显式画质上传、同画质对比、旧库迁移、前端多画质预览/网格、浏览器手动上报和 ArashiTestCase 上报脚本均已落地；验收结果见本文末尾审计清单及项目测试命令。

> 决策日期：2026-08-20
>
> 适用项目：PixelComparison
>
> 设计范围：采集包、上报脚本、后端存储与接口、截图对比、批次管理、数据库迁移、测试与发布

## 1. 文档目的

本文定义 PixelComparison 从“一个批次只包含一个截图画质”演进到“一个批次可包含多个截图画质运行，并可同时包含一份烘培数据”的完整方案。

本文是实现、代码审查、数据迁移和验收的共同依据。除本文明确列为后续事项的内容外，实现不得自行改变批次、画质、覆盖、对比或部分完成的语义。

领域术语以项目根目录的 `CONTEXT.md` 为准。本文在此基础上补充数据结构、接口、失败语义和执行顺序。

## 2. 已确认结论摘要

1. 批次号继续全局唯一；一个批次只属于一个分支、一个场景和一个平台。
2. 一个批次可以包含零个或多个画质运行，以及零或一份烘培数据。
3. `shading_quality` 是业务画质身份；`tex_quality` 仅作为采集参数保存，不参与筛选、唯一性或对比匹配。
4. 同一批次的同一 `shading_quality` 最多出现一次；重复即判定整个 manifest 无效，后端不得创建批次。
5. 采集阶段的任一计划画质失败时，不产生可上报 manifest；“采集阶段部分成功”不纳入本期需求。
6. 上传阶段可以出现部分失败。已经完整写入的画质运行和烘培数据可继续使用，但上报脚本必须返回失败。
7. 同名批次已存在且未指定 `--overwrite` 时必须整体失败；不支持跨上报进程续传或补传。
8. `--overwrite` 表示删除同名旧批次及其派生数据后，从头重建整个批次。
9. 单个 HTTP 请求因网络中断重试时允许幂等；使用 SHA-256 区分“同内容重试”和“同键不同内容冲突”。
10. 自动对比和手动对比都必须是同一 `shading_quality`，禁止跨画质对比。
11. 烘培数据属于批次，不属于任何画质运行，也不按画质筛选。
12. 批次管理继续一批次一行；现有“画质”列展示多个画质标签，不增加额外的运行数或截图数列。
13. 截图预览优先打开电影画质（`shading_quality=5`）；不存在时回退到最高的完整画质，并允许切换其他完整画质。
14. 截图对比选择“全部画质”时，一个批次展开为多列；同批次内按画质从高到低排列。
15. 旧格式和新格式上报接口在迁移期共存；旧截图接口仅能服务可唯一推断画质的批次。
16. 旧数据库自动迁移；迁移前必须成功创建独立备份，否则后端拒绝启动。
17. 图片上传默认 4 个并发工作线程，可配置；对比计算全局默认最多 2 个工作线程，可配置。

## 3. 目标与非目标

### 3.1 目标

- 一次采集和一次上报即可保存多个画质档位的截图，减少重复启动、采集和上报成本。
- 保持批次作为 CI/P4/分支/场景维度的单一审计记录。
- 允许仅截图、仅烘培数据、截图与烘培数据同时存在三种有效批次。
- 在批次管理、截图预览、截图对比和自动对比中正确表达画质运行。
- 平滑读取和迁移现有单画质数据库、现有图片路径和旧上报脚本。
- 在 SQLite 和远程图片目录环境下控制上传、缩略图及对比任务并发，避免阻塞查询。
- 给异常数据、重复上报、上传中断、覆盖和回滚定义可测试的确定行为。

### 3.2 非目标

- 不接受采集程序输出“部分画质采集成功”的有效 manifest。
- 不支持跨 `shading_quality` 对比，也不提供画质归一化或画质差异分析。
- 不支持同一批次号的隐式续传、增量补档或后到画质合并。
- 不把所有图片打成一个超大压缩包再上传。
- 不搬迁旧图片和旧缩略图文件；数据库记录继续指向原路径。
- 不把烘培数据复制到每个画质运行。
- 不以 `quality_run_index` 作为业务画质身份。
- 不在本期引入鉴权、对象存储或多节点任务队列。
- 不修改烘培数据页面现有的场景、节点、趋势和统计口径语义。

## 4. 输入格式与现有样本

设计以以下实际采集目录为输入依据：

| 样本 | 画质运行 | 截图 | 烘培数据 | 预期批次类型 |
|---|---:|---:|---:|---|
| `PixelComparison` | 3 | 每档 32 张 | 有 | 多画质完整批次 |
| `PixelComparison_NoScreenshot` | 0 | 0 | 有 | 仅烘培批次 |
| `PixelComparison_NoMapbuildData` | 3 | 每档 32 张 | 无 | 多画质截图批次 |

新采集包的核心结构如下，字段名称以生产 manifest 为准：

```json
{
  "format_version": 2,
  "capture_type": "levelsequence",
  "ue_data": {
    "world_name": "Volcano_WP",
    "platform": "WindowsEditor",
    "tex_quality_levels": [0, 2, 4],
    "run_stages": "screenshot,mapbuilddata",
    "resolution": {"width": 1920, "height": 1080}
  },
  "quality_runs": [
    {
      "quality_run_index": 0,
      "tex_quality": 0,
      "shading_quality": 5,
      "status": "complete",
      "screenshot_dir": "Screenshot/0",
      "screenshot_count": 32,
      "screenshots": [
        {
          "index": 0,
          "name": "Seq_Volcano_WP_0000",
          "image": "Screenshot/0/Seq_Volcano_WP_0000.png",
          "camera": {}
        }
      ]
    }
  ],
  "artifacts": {
    "map_build_data": {
      "path": "Artifacts/MapBuildData/map_build_data.json",
      "format": "map-build-data/v2",
      "status": "complete"
    }
  }
}
```

适配器负责把生产字段映射为统一写入计划：`ue_data.world_name → scene_id`、`screenshots[*].name → scene_name`、`image → source_relative_path`、`index → frame_index`。`screenshot_count` 必须等于数组长度；`ue_data.tex_quality_levels` 必须与各运行的 `tex_quality` 集合及采集器声明顺序一致，但业务画质唯一性仍只看 `shading_quality`。

当前 v2 样本不携带批次号、分支、P4、批次 URL 和完整上报时间。这些流水线元数据继续由上报脚本参数注入。若未来 manifest 增加 `pipeline_data`，取值优先级固定为：

1. 显式 CLI 参数；
2. `pipeline_data`；
3. 脚本已有安全默认值。

`branch_tag` 进入后端前继续规范化为小写；批次号不允许通过默认值静默生成，除非现有脚本已有明确且可审计的生成规则。

## 5. 领域模型与不变量

### 5.1 聚合关系

```text
Batch（批次，聚合根）
├── QualityRun[0..N]（画质运行）
│   └── Screenshot[1..N]（截图）
└── MapBuildSnapshot[0..1]（烘培数据快照）
    └── MapBuildRegistry[0..N]（规范化 Registry 指标）
```

对比和基线引用画质运行，而不是只引用批次：

```text
Comparison
├── current_quality_run_id
└── reference_quality_run_id

Baseline
└── source_quality_run_id
```

### 5.2 身份与唯一性

- 批次身份：`batch_id`，全局唯一。
- 画质运行的稳定外部身份：`(batch_id, shading_quality)`。
- `quality_run_index` 仅用于保留采集顺序和审计，不参与筛选、对比或 URL 的稳定身份。
- 截图身份：`(quality_run_id, scene_name)`。
- 烘培数据身份：`batch_id`，一批次最多一份。
- 一个 manifest 中 `quality_run_index` 和 `shading_quality` 都不得重复。
- `shading_quality` 的有效值沿用当前项目规则 `0..5`。

### 5.3 完整性

画质运行只有同时满足以下条件才是“完整画质运行”：

```text
capture_status == "complete"
AND expected_screenshot_count > 0
AND ready_screenshot_count == expected_screenshot_count
```

其中：

- `capture_status` 来自通过结构校验的 manifest；本期有效上报只接受 `complete`。
- `expected_screenshot_count` 是 manifest 声明的截图条目数。
- `ready_screenshot_count` 由数据库中 `upload_status=ready` 的截图计划行数计算，不单独持久化，避免状态漂移。
- 画质运行的可用状态必须由服务器计算，客户端不可直接指定 `is_complete=true`。
- 一个批次只要包含至少一个完整画质运行，就具备截图能力。
- 上传中断产生的非完整运行保留为诊断信息，但不能预览、设为基线或参与对比。
- 烘培数据能力独立于画质运行完整性。

旧客户端和迁移数据存在一个受限兼容例外：`capture_status=legacy` 且至少有一张 `ready` 截图的唯一画质运行继续视为可用，以保持升级前行为。只有迁移器和旧接口兼容分支能产生 `legacy`；新版 v1/v2 上报适配器均应提交完整截图计划并使用 `complete`。该例外不得用于接收新格式的部分采集结果。

### 5.4 批次写入状态

为避免在 SQLite 中维护容易失真的总状态字段，批次能力和完整性均从子记录派生：

| 状态 | 判定 | 可见性/能力 |
|---|---|---|
| 完整多画质批次 | 所有声明运行完整，烘培数据按 manifest 要求成功 | 所有对应功能可用 |
| 部分完成批次 | 至少一项成功，但有截图文件或烘培数据上传失败 | 批次管理可见；仅成功能力可用；上报脚本失败退出 |
| 待补传批次 | 批次和运行声明已创建，但没有任何完整画质及烘培数据 | 仅用于诊断；重新上报必须 `--overwrite` |
| 仅烘培批次 | 无画质运行，有烘培数据 | 烘培功能可用，截图相关功能禁用 |

采集阶段失败不属于上述状态，因为结构校验前不会向后端创建批次。

## 6. 当前实现差距

当前代码不能仅通过扩展 DTO 支持该需求，主要原因如下：

- `batches.shading_quality` 把画质直接放在批次上，只能表达单画质。
- `screenshots` 以 `(batch_id, scene_name)` 唯一，多画质下相同检查点会冲突。
- 截图路径为 `batches/{batch_id}/{scene_name}.png`，不同画质会覆盖。
- `comparisons` 和 `baselines` 只引用批次，无法唯一定位批次内画质。
- 手动对比当前没有可持久化的画质身份，无法从模型层禁止跨画质。
- v2 manifest 把截图放在 `quality_runs[*].screenshots`，现有上报脚本读取旧的顶层 `screenshots`，会把 v2 误判为无截图。
- 当前数据库建表和字段迁移发生在应用生命周期备份启动之前，不满足“先备份、后迁移、失败拒绝启动”的要求。
- 当前对比任务按请求直接创建线程，不适合多画质展开后增加的并发任务量。

因此，画质运行必须成为后端一级实体；不能只在截图 JSON 或前端列模型中临时拼接。

## 7. 目标模块边界

### 7.1 上报端：ManifestAdapter

上报脚本应先把不同采集格式解析为统一且不可变的 `BatchIngestPlan`，再执行 HTTP 写入：

```text
v1 manifest ─┐
             ├─ ManifestAdapter.parse() ─ BatchIngestPlan ─ UploadExecutor
v2 manifest ─┘
```

`BatchIngestPlan` 至少包含：

- 批次元数据；
- 有序的画质运行声明；
- 每个运行的截图文件清单；
- 可选烘培数据文件；
- manifest 格式版本和源文件摘要。

格式兼容、路径解析和结构校验集中在适配器内。上传执行器不再判断 v1/v2 字段差异。

### 7.2 后端：批次写入服务

HTTP 路由只负责验证协议、打开事务和映射响应。新格式通过一次原子创建请求提交批次、全部画质运行和截图计划，确保重复画质等结构错误不会留下空批次。以下规则集中到可测试的服务层：

- 创建/覆盖批次；
- 注册画质运行；
- 上传截图及幂等判断；
- 计算完整性和能力；
- 删除批次及关联文件；
- 选择可比较画质运行；
- 兼容旧接口时的唯一画质推断。

建议从过度集中的 `backend/app/main.py` 中提取 `ingest`、`quality_runs` 和 `comparison_scheduler` 模块；路由不得重复实现领域校验。

### 7.3 前端：画质运行投影

批次管理仍使用“批次投影”；截图对比使用“画质运行列投影”。二者不能复用同一个数组并依靠条件字段切换：

- 批次投影：一批次一行，展示所有声明画质。
- 画质运行列投影：一完整画质运行一列，稳定键为 `batch_id:shading_quality`。

## 8. 数据库设计

### 8.1 `quality_runs` 新表

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | INTEGER | 主键，自增；仅内部引用 |
| `batch_id` | TEXT | 外键 `batches.id`，级联删除，索引 |
| `quality_run_index` | INTEGER | 非负，采集顺序 |
| `shading_quality` | INTEGER | `0..5`，业务画质 |
| `tex_quality` | INTEGER NULL | 采集参数，不参与业务匹配 |
| `capture_status` | TEXT | 新数据仅允许 `complete`；迁移数据可记 `legacy` |
| `expected_screenshot_count` | INTEGER | 新数据必须大于 0 |
| `created_at` | DATETIME | 服务端创建时间 |

约束与索引：

- `UNIQUE(batch_id, shading_quality)`；
- `UNIQUE(batch_id, quality_run_index)`；
- `INDEX(shading_quality, batch_id)`；
- 检查约束或服务层等价校验 `0 <= shading_quality <= 5`；
- 新上报禁止零截图画质运行。仅烘培批次应传空 `quality_runs`，而不是创建零截图运行。

### 8.2 `screenshots` 调整

新增/调整字段：

| 字段 | 说明 |
|---|---|
| `quality_run_id` | 外键 `quality_runs.id`，新的所属关系和查询键 |
| `upload_status` | `pending/ready/failed`；新 manifest 注册时先创建 `pending` 计划行 |
| `source_relative_path` | manifest 中的安全相对路径，仅用于审计与上报映射 |
| `sha256` | 新上传文件 SHA-256；迁移旧数据可为空 |
| `byte_size` | 新上传文件字节数；迁移旧数据可为空 |

约束从 `UNIQUE(batch_id, scene_name)` 改为：

```text
UNIQUE(quality_run_id, scene_name)
```

新格式创建批次时，在同一个事务中为 manifest 声明的每张截图建立 `pending` 行；上传成功后补齐服务端存储 `path`、摘要、大小和缓存版本，并切换为 `ready`。所有业务截图查询必须过滤 `ready`。这样后端可以验证上传的检查点确实来自已接受 manifest，也能区分“计划 32 张、已写入 31 张”和“manifest 本来只声明 31 张”。

`path` 对新建的 `pending` 行允许为空；迁移旧行直接标记 `ready`。`failed` 只用于记录服务端已经接收但校验/发布失败的尝试，普通网络未到达服务端时仍保持 `pending`。

迁移期可以保留 `batch_id` 作为冗余兼容字段，但它必须由所属 `quality_run` 推导且不可独立修改。完成所有调用点迁移后再在后续版本删除；本期不要求一次性删除，以降低 SQLite 重建风险。

### 8.3 `batches` 调整

- `batches.shading_quality` 暂时保留为兼容字段。
- 单画质批次可返回该值；多画质或无画质批次返回 `null`。
- 新代码不得再把该字段作为截图查询或对比的事实来源。
- 建议增加 `manifest_format_version` 和 `source_manifest_sha256`，用于审计采集格式及覆盖来源；它们不参与业务唯一性。

### 8.4 对比与基线

`comparisons` 新增：

- `current_quality_run_id`；
- `reference_quality_run_id`；
- `scope_status`，新数据固定为 `valid`，仅用于标记无法映射到同画质的历史记录。

前两个字段是新数据的事实来源。旧的 `batch_id/ref_batch_id` 在本期保留，便于列表、清理和兼容；服务层必须验证两个引用分别属于对应批次，且 `shading_quality` 相等。新记录的两个运行引用非空；只有迁移发现的历史不兼容记录可以为空，且 `scope_status=legacy_incompatible`，它们不得被 lookup 或前端复用。

建议增加唯一索引：

```text
UNIQUE(current_quality_run_id, reference_quality_run_id)
```

实现时应使用仅覆盖两个运行引用非空记录的部分唯一索引。如现有系统允许强制重算，强制重算更新同一比较记录及明细，不创建同对重复记录。

`baselines` 新增 `source_quality_run_id`。一个基线明确对应一个画质运行，不能只表达“批次是基线”。

### 8.5 烘培数据

`map_build_snapshots.batch_id` 及 Registry 结构不变。可增加 `content_sha256` 和 `byte_size` 支持幂等重试与审计，但不得增加 `quality_run_id`。

### 8.6 文件路径

新截图使用：

```text
images/batches/{safe_batch_id}/{shading_quality}/{safe_scene_name}.png
```

缩略图继续由现有缩略图服务管理，并以原图相对路径为输入，因此自然包含画质目录。旧截图路径不搬迁、不重命名。

写文件必须采用同一文件系统内的“临时文件 + 原子替换”：

1. 流式写入临时文件，同时计算 SHA-256 和大小；
2. 验证图片格式和限制；
3. 在数据库事务中确认唯一键与内容摘要；
4. 原子发布正式文件；
5. 提交数据库；
6. 失败时清理临时文件，并由定期清理处理极少量事务/文件边界残留。

## 9. 后端 API 设计

接口路径以下均以 `/api` 为前缀。

### 9.1 原子创建批次和画质计划

保留：

```http
POST /api/batches
```

旧格式请求继续只包含批次元数据和 `overwrite`。新格式在同一请求中额外提交全部画质运行及其截图计划，但不再要求在批次层传业务 `shading_quality`：

```json
{
  "id": "1240",
  "branch_tag": "main",
  "scene_id": "Coral_WP",
  "platform": "Windows",
  "p4_version": 1232111,
  "overwrite": false,
  "manifest_format_version": 2,
  "source_manifest_sha256": "...",
  "quality_runs": [
    {
      "quality_run_index": 0,
      "shading_quality": 5,
      "tex_quality": 0,
      "capture_status": "complete",
      "screenshots": [
        {
          "scene_name": "Seq_Coral_WP_0000",
          "source_relative_path": "Screenshot/0/Seq_Coral_WP_0000.png",
          "frame_index": 0,
          "camera": {}
        }
      ]
    }
  ]
}
```

后端必须在一个数据库事务内验证并创建 `Batch + QualityRun + pending Screenshot`。重复画质、重复 index、重复检查点、非法路径或非法状态会回滚整个事务，因此不会留下批次或运行记录。

规则：

- 批次不存在：创建聚合根。
- 批次存在且 `overwrite=false`：返回 `409 BATCH_ALREADY_EXISTS`，不得继续上传或修改任何子数据。
- 批次存在且 `overwrite=true`：在服务端执行现有完整覆盖语义，删除旧截图、缩略图、烘培数据、对比记录和热力图，再创建新批次。
- 覆盖不是合并；旧批次任何未在新 manifest 中出现的画质和烘培数据都会消失。
- 分支、场景、平台在批次创建后不可修改。
- 覆盖请求必须先完成全部请求体校验，再在一个数据库事务中删除旧聚合并创建新计划；校验或事务失败时旧批次保持不变。旧文件清理只在事务成功后执行，并且必须在新截图上传开始前完成，避免清理任务误删同路径新文件。

`quality_runs=[]` 是仅烘培批次的合法输入。普通请求不可在创建后增加、删除或改写运行及截图计划；调整必须重新 `--overwrite` 整批。响应可以返回服务器生成的 `quality_run_id`，但后续外部路径仍使用稳定的 `shading_quality`，避免客户端依赖内部 ID。

未升级的旧客户端仍可按原流程先创建单画质批次、再调用旧截图接口；后端为它创建唯一的 `legacy` 兼容画质运行，并在每次旧上传时创建/填充截图行。该运行在至少一张截图就绪后沿用旧系统的可用语义，因为旧协议没有期望截图总数或 finalize。升级后的上报脚本即使读取 v1 manifest，也应转换为上述原子创建请求以获得精确完整性。旧兼容分支不得用于 v2 多画质请求。

### 9.2 上传截图

新增：

```http
POST /api/batches/{batch_id}/quality-runs/{shading_quality}/screenshots
```

表单至少包含 `scene_name` 和图片文件。`frame_index` 与 `camera` 已在截图计划中注册；为兼容现有脚本可以重复提交，但必须与计划一致，否则返回 `409 SCREENSHOT_METADATA_CONFLICT`。

规则：

- 目标画质必须已注册。
- `scene_name` 必须对应原子创建阶段生成的截图计划行。
- 同 `(batch_id, shading_quality, scene_name)` 首次上传成功返回 `201`。
- 同键、同 SHA-256 的请求视为同一次请求重试，返回 `200`，不重写文件、不重复生成缩略图。
- 同键、不同 SHA-256 返回 `409 SCREENSHOT_CONTENT_CONFLICT`。
- 超过声明截图数量、非法图片、过大文件或不安全名称返回 `422`/`413`。
- 请求结束后由服务器实时派生该运行是否完整；无需显式 finalize。

旧接口：

```http
POST /api/batches/{batch_id}/screenshots
```

仅在以下任一条件成立时可继续使用：

- 旧批次具有唯一兼容画质；
- 新批次只注册了一个画质运行。

多画质批次调用旧接口返回 `422 AMBIGUOUS_QUALITY_RUN`，不得猜测电影画质。

### 9.3 上传烘培数据

保留：

```http
POST /api/batches/{batch_id}/map-build-data
```

烘培数据仍只与批次关联。相同内容请求重试幂等返回成功，不同内容冲突返回 `409 MAP_BUILD_CONTENT_CONFLICT`；改变内容必须整批覆盖。

### 9.4 批次列表和详情

`GET /api/batches` 一批次只返回一行。响应新增：

```json
{
  "id": "1240",
  "branch_tag": "main",
  "scene_id": "Coral_WP",
  "shading_quality": null,
  "shading_qualities": [5, 3, 1],
  "available_shading_qualities": [5, 3],
  "has_screenshots": true,
  "has_map_build_data": true,
  "quality_runs": [
    {
      "shading_quality": 5,
      "tex_quality": 0,
      "expected_screenshot_count": 32,
      "ready_screenshot_count": 32,
      "is_complete": true
    }
  ]
}
```

字段语义：

- `shading_qualities`：声明过的全部画质，用于批次管理的多画质标签展示；包括上传阶段未完整的运行。
- `available_shading_qualities`：完整且可用于预览/对比的画质。
- `has_screenshots`：`available_shading_qualities` 非空。
- 兼容字段 `shading_quality`：恰好一个声明画质时返回该画质；多画质或无画质时为 `null`。

批次管理不提供画质筛选，始终按分支、场景和日期展示批次；`shading_qualities` 只作为该批次画质列的展示数据。

### 9.5 截图列表、预览和网格

新增明确画质的查询：

```http
GET /api/batches/{batch_id}/quality-runs/{shading_quality}/screenshots
```

仅完整运行可作为常规预览数据源。非完整运行返回 `409 QUALITY_RUN_INCOMPLETE`；管理型详情可以通过批次详情看到上传计数。

旧 `GET /api/batches/{batch_id}/screenshots`：

- 只有一个完整画质时自动推断；
- 多个完整画质时返回 `422 AMBIGUOUS_QUALITY_RUN`；
- 不得默认选择电影画质，默认规则由前端显式选择后调用新接口。

场景网格接口 `GET /api/scenes/{scene_id}/grid` 增加 `shading_quality`：

- 数字值：每批次最多返回该画质一列，只返回完整运行。
- `all`：将每个完整画质运行展开为独立列。
- 列稳定键：`{batch_id}:{shading_quality}`。
- 批次之间继续沿用当前时间排序；同一批次内按 `shading_quality` 从高到低。
- 热力图列继续固定在最右侧，并只对当前选中的同画质基线/对比组合生效。

### 9.6 对比

创建请求改为：

```json
{
  "batch_id": "1240",
  "ref_batch_id": "1239",
  "shading_quality": 5,
  "force": false
}
```

服务端解析两个 `(batch_id, shading_quality)`，并验证：

- 两个批次分支相同；
- 场景相同；
- 平台相同；
- 两个画质运行都完整；
- 两边 `shading_quality` 与请求值相同。

不提供 `current_shading_quality` 和 `ref_shading_quality` 两个独立字段，从协议层减少跨画质组合的可能。

兼容旧请求时，只有双方都恰好有一个相同的完整画质才允许推断；否则返回 `422 SHADING_QUALITY_REQUIRED`。

对比查找接口必须增加 `shading_quality` 参数，查找键由批次对升级为画质运行对。已有热力图和 `comparison_items` 仍可复用。

自动对比对目标批次的每个完整画质分别寻找候选：同分支、同场景、同平台、同 `shading_quality`。响应返回任务数组或按画质分组的结果，不得跨画质回退到“最近批次”。

### 9.7 基线

设为基线的输入必须包含 `batch_id + shading_quality`。仅完整画质运行可设为基线。前端选择某一画质基线后，其他画质的“设为基线”“设为对比”等角色操作保持禁用，直到清除当前选择。

### 9.8 错误契约

| 场景 | HTTP | 错误码 | 是否允许已有数据变化 |
|---|---:|---|---|
| manifest 结构非法 | 422 | `INVALID_MANIFEST` | 否，不创建批次 |
| 重复 `shading_quality` | 422 | `DUPLICATE_SHADING_QUALITY` | 否，不创建批次 |
| 重复 `quality_run_index` | 422 | `DUPLICATE_QUALITY_RUN_INDEX` | 否，不创建批次 |
| 批次已存在且未覆盖 | 409 | `BATCH_ALREADY_EXISTS` | 否 |
| 相同截图键、不同内容 | 409 | `SCREENSHOT_CONTENT_CONFLICT` | 否 |
| 多画质调用旧接口 | 422 | `AMBIGUOUS_QUALITY_RUN` | 否 |
| 预览/对比非完整运行 | 409 | `QUALITY_RUN_INCOMPLETE` | 否 |
| 缺少可推断画质 | 422 | `SHADING_QUALITY_REQUIRED` | 否 |
| 跨画质或跨分支对比 | 400 | `COMPARISON_SCOPE_MISMATCH` | 否 |
| 文件过大 | 413 | `UPLOAD_TOO_LARGE` | 否 |

所有错误响应应包含稳定的 `code`、面向用户的 `message` 和可选 `details`，脚本不得依赖中文文本判断分支。

## 10. 上报脚本设计

目标脚本：`C:\WorkSpace\ArashiTestCase\Cases\Heatmap\PixelComparisonReport.py`。

### 10.1 解析与校验

脚本必须在发出第一个写请求前完成全部结构校验：

- 支持旧顶层 `screenshots` 和新 `quality_runs[*].screenshots`；
- 校验格式版本及必需字段；
- 校验 `shading_quality`、`quality_run_index` 唯一；
- 校验 `shading_quality` 范围；
- 只接受 `status=complete` 的画质运行；
- 校验每个画质运行至少一张截图；
- 校验同运行 `scene_name` 唯一；
- 校验相对路径，禁止绝对路径、`..` 越界和链接逃逸；
- 校验声明的文件类型和 map build artifact 字段；
- 校验所有计划运行均存在于有效 manifest，采集阶段部分失败直接拒绝上报。

结构错误时不得创建批次。

本地文件缺失属于上传阶段错误而非 manifest 结构错误：脚本可以在批次及运行注册后发现，并形成部分完成批次，但必须输出缺失清单并以非零码退出。下一次重报需显式 `--overwrite`。

### 10.2 上传阶段

固定阶段：

1. 解析并完整校验采集包；
2. `POST /api/batches` 在一个事务中创建或显式覆盖批次、全部运行和截图计划；
3. 使用有界线程池上传截图；
4. 若存在则上传烘培数据；
5. 拉取批次详情复核每档实际/期望数量和烘培数据能力；
6. 输出逐画质汇总并设置退出码。

脚本不得在收到 `BATCH_ALREADY_EXISTS` 后继续“补充”截图或烘培数据。

### 10.3 参数

保留现有参数，并增加或明确：

```text
--branch_tag main
--overwrite
--upload-workers 4
```

- `--upload-workers` 默认 4，建议限制 `1..8`；也可由 `PIXELCOMP_UPLOAD_WORKERS` 提供默认值，CLI 优先。
- 无截图或无烘培数据均为合法输入，只要采集包结构符合对应模式。
- 同名批次无 `--overwrite` 一律失败；脚本不得自动加覆盖。

### 10.4 重试语义

- 仅对连接错误、超时、`429` 和可恢复 `5xx` 做有限指数退避重试。
- `4xx` 除明确的幂等成功响应外不重试。
- 单文件请求因“服务端已写入但客户端未收到响应”而重试时，后端以 SHA-256 返回成功。
- 同批次跨进程重启脚本不是重试，而是重复上报，必须 `--overwrite`。

### 10.5 退出码与输出

成功条件：所有声明截图均完整上传，且 manifest 声明的烘培数据也上传成功。

输出至少包含：

```text
batch=1240 branch=main scene=Coral_WP
quality=5 expected=32 uploaded=32 complete=yes
quality=3 expected=32 uploaded=31 complete=no failed=1
map_build=uploaded
result=failed
```

任一文件失败、数量不一致或最终复核失败，进程退出码必须非零，即使批次中已有部分数据可用。

## 12. 数据迁移

### 12.1 启动顺序

当前“模块导入时建表/迁移、应用生命周期中才启动备份”的顺序必须调整为显式初始化：

```text
加载配置
→ 检查数据库版本
→ 如需迁移，创建迁移前备份
→ 校验备份可读
→ 执行版本化迁移
→ foreign_key_check / quick_check
→ 启动缩略图、每日备份和 HTTP 服务
```

迁移前备份失败、备份校验失败或迁移校验失败时，后端必须拒绝完成启动，不能带着未知结构继续服务。

建议使用数据库 schema version，而不是只通过“列是否存在”猜测迁移状态。迁移需幂等，但正常情况下每个版本只执行一次。

### 12.2 迁移前备份

- 使用现有 SQLite Online Backup 实现，确保 WAL 中已提交数据进入快照。
- 备份与每日备份区分，例如：

```text
data/backup/2026-08-20/db/shotdiff.pre-multi-quality-v1.20260820T153000.db
```

- 备份后以只读连接执行 `PRAGMA quick_check`；结果非 `ok` 时终止。
- 不只复制 `shotdiff.db` 文件来代替在线备份，避免遗漏 WAL 已提交内容。

### 12.3 迁移步骤

1. 创建 `quality_runs` 新表。
2. 对每个存在截图的旧批次创建一个迁移画质运行：
   - `shading_quality = batches.shading_quality`；
   - 旧值为空时使用项目现有兼容默认“极致”画质 `4`；
   - `tex_quality = null`；
   - `quality_run_index = 0`；
   - `capture_status = legacy`；
   - `expected_screenshot_count = 实际旧截图数`。
3. 仅烘培、无截图的旧批次不创建画质运行。
4. 按 SQLite 安全重建方式升级 `screenshots`，回填 `quality_run_id`，保留截图 ID、路径、缓存版本、帧号和相机数据。
5. 将截图唯一约束替换为 `(quality_run_id, scene_name)`。
6. 为旧 `comparisons` 回填当前/参照画质运行：双方迁移画质相同时标记 `scope_status=valid`；不一致时保留原记录与明细、将运行引用留空并标记 `scope_status=legacy_incompatible`。这些历史结果不再参与 lookup、展示或强制重算，按现有 14 天保留策略自然过期。迁移日志必须记录数量和 ID，不能静默改画质或把它们伪装成有效结果。
7. 为旧 `baselines` 回填 `source_quality_run_id`。
8. 创建新索引和外键。
9. 执行计数、孤儿、唯一性、外键和 `quick_check` 校验。
10. 成功后写入新 schema version。

该默认值已经由当前后端常量、现有测试和上报文档共同定义为 `4`；它只用于迁移缺失画质的历史数据，不影响新前端默认预览电影画质 `5`。迁移代码必须把采用值写入日志和迁移测试夹具。

### 12.4 不迁移的内容

- 不移动旧图片和缩略图。
- 不为全部旧远程图片启动时计算 SHA-256，避免阻塞启动；迁移记录的摘要允许为空。
- 不重算旧热力图。
- 不把仅烘培批次伪造成零截图画质运行。

### 12.5 回滚

1. 停止新版本后端，确保无写请求。
2. 保存当前失败库和日志用于审计。
3. 用迁移前在线备份恢复数据库。
4. 部署旧版本代码并启动。
5. 新版本产生的画质子目录视为孤儿文件，回滚过程不自动删除；确认恢复后由单独工具按数据库引用清理。

## 13. 并发、性能与稳定性

### 13.1 图片上传

- 上报脚本使用 `ThreadPoolExecutor` 或等价有界池，默认 4，最大建议 8。
- 每个工作线程只流式持有当前文件，禁止一次把所有画质图片读入内存。
- 后端文件哈希在流式写入时计算，禁止写完再读一遍远程盘。
- 数据库事务只包围必要元数据操作，不在持有 SQLite 写锁期间生成缩略图或执行图片解码。
- 缩略图继续进入现有有界后台队列；上传响应不等待整批缩略图完成。

### 13.2 对比任务

- 把按请求创建的无界线程改为全局有界执行器。
- 默认最大并发 2，通过 `PIXELCOMP_COMPARE_WORKERS` 配置，合理范围 `1..4`。
- 同一画质运行对继续 inflight 去重；重复请求返回现有任务。
- 队列满时请求可以进入有界等待队列；达到队列上限应返回明确的 `429/503`，不能无限占用内存。
- 对比状态和任务进度继续可轮询；异常必须释放运行中标记。

### 13.3 查询

- 批次列表使用聚合子查询或预加载一次返回画质摘要，禁止一行批次一次查询的 N+1。
- 场景网格先按分支、场景、日期和完整画质运行筛选，再查询截图。
- 网格只返回缩略图 URL；原图继续点击后懒加载和相邻预加载。
- 所有缓存和 inflight 键增加 `shading_quality`，避免同批次不同画质串图。
- 保持 SQLite WAL 和现有 `busy_timeout`；耗时图片、缩略图、对比计算不得运行在数据库写事务内。

### 13.4 基础性能验收

以下指标在与生产相近的远程图片目录和 SQLite 配置上执行，并记录硬件、网络和数据量：

- 3 档 × 32 张图片上报时，进程内存不随总文件数线性增长，峰值主要受工作线程数和单图大小控制。
- 4 路图片上传并发、同时 5 个前端查询客户端时，批次列表、元数据和场景网格不得出现 5xx 或数据库锁超时。
- 上述并发下常用元数据接口 P95 不高于空闲基线的 2 倍；若绝对值超过 1 秒需记录并分析。
- 对比实际运行线程数永远不超过配置值，额外任务排队而不是生成新线程。
- “全部画质”30 列、100 个检查点的网格首屏接口和前端渲染需要单独留存耗时，不得一次加载原图。

## 14. 安全与数据校验

- 批次号、场景名和相对路径必须经过安全段校验，禁止路径穿越和绝对路径。
- 上传内容必须解码验证为支持的图片格式，不能只相信扩展名或 MIME。
- 单文件大小和请求大小应由配置限制，超限返回 `413`。
- 后端重新计算 SHA-256、文件大小、计划行数和 `ready` 行数，不信任客户端摘要或计数。
- `branch_tag` 规范化后写入且不可变。
- 全局批次唯一性由数据库主键保证；应用层预检查不能替代数据库约束。
- 跨分支、跨场景、跨平台和跨画质对比必须由后端拒绝，不能只依赖前端禁用。
- `overwrite` 是破坏性操作；日志必须记录操作者来源、批次、旧能力摘要和新 manifest 摘要。
- 覆盖和删除的数据库操作与文件清理要遵循“先确定引用、事务提交、再清理孤儿”的现有安全策略，失败文件进入可重试清理队列。

## 20. 决策记录与未采用方案

| 决策 | 采用方案 | 未采用方案及原因 |
|---|---|---|
| 批次与画质关系 | 批次聚合多个画质运行 | 每画质一个批次会继续增加采集/上报次数，并割裂同一次 CI 记录 |
| 业务画质身份 | `shading_quality` | `tex_quality` 是采集参数；index 不稳定且不具业务语义 |
| 截图归属 | 一级 `quality_runs` 实体 | 仅给截图加画质无法表达运行完整性、期望数量、对比和基线身份 |
| 烘培归属 | 批次级 0..1 | 每画质复制会冗余且错误暗示烘培数据受画质影响 |
| 采集部分失败 | 不上报 | 接受会使计划档位和 manifest 完整性难以审计 |
| 上传部分失败 | 保留成功数据，脚本失败 | 整批数据库事务无法覆盖长时间文件上传；完全回滚会浪费已成功大文件 |
| 重复批次 | 无覆盖严格失败 | 隐式补传会让同批次内容随时间变化且难以确认来源 |
| 覆盖 | 删除后整批重建 | 按档位合并会留下旧 manifest 未声明数据 |
| 文件传输 | 有界并行逐文件 | 单一大包内存/临时空间/失败重传成本高 |
| 对比协议 | 两批次 + 一个共享画质 | 两个独立画质参数容易产生非法跨画质组合 |
| 旧图片迁移 | 保持原路径 | 启动时搬迁远程大目录风险高、耗时长且回滚困难 |
| 完整性状态 | 从计划行和 `ready` 行派生 | 存 `is_complete` 易与实际文件/行数漂移 |

# PixelComparison 数据上报接入指南

本文面向 UE 采集模块、渲染农场和 CI。目标是把一次采集产生的批次元数据、检查点截图和/或烘培数据可靠上报到 PixelComparison，并在具备截图时按需发起自动对比。

默认开发后端地址是 `http://127.0.0.1:8020`。接口没有鉴权，只能在可信网络使用。

## 1. 上报流程

一次完整上报分为三类数据和一个可选动作：

```text
POST /api/batches
        │ 原子创建批次、全部画质运行和截图计划，取得最终 batch id
        ├────────────────────────────────────────────┐
        ▼                                            ▼
POST /api/batches/{id}/map-build-data   POST /api/batches/{id}/quality-runs/{q}/screenshots
        │ 可选；每批一份，同内容幂等               │ 每张截图写入预声明的画质槽位
        └──────────────────────┬─────────────────────┘
                               ▼
POST /api/batches/{id}/auto-compare
          可选；全部截图上传完成后调用一次，为每档画质分别匹配
```

截图与烘培数据可以独立上传，也允许创建没有画质运行的纯烘培/诊断批次。声明为 `complete` 的画质只有在计划中的全部截图都上传且内容校验成功后才可用于预览、网格和对比；自动对比会忽略尚未完整的画质。生产上报端仍应只在全部截图成功后触发自动对比。

## 2. 推荐数据包结构

新采集端应使用 `format_version: 2`。每个 `quality_runs[]` 元素代表一次完整画质运行；`shading_quality` 是筛选和对比身份，`tex_quality` 仅作为采集参数保存。

```text
<批次目录>/
  manifest.json
  Screenshot/
    0/                       # quality_run_index=0，电影档
      Seq_Starfall_0000.png
    1/                       # quality_run_index=1，精美档
      Seq_Starfall_0000.png
  Artifacts/
    MapBuildData/
      map_build_data.json
```

最小 v2 manifest 示例：

```json
{

  "pipeline_data": {

  },
  "quality_runs": [
    {
      "quality_run_index": 0,
      "shading_quality": 5,
      "tex_quality": 0,
      "status": "complete",
      "screenshot_count": 1,
      "screenshots": [
        {
          "index": 0,
          "name": "Seq_Starfall_0000",
          "image": "Screenshot/0/Seq_Starfall_0000.png"
        }
      ]
    },
    {
      "quality_run_index": 1,
      "shading_quality": 3,
      "tex_quality": 2,
      "status": "complete",
      "screenshot_count": 1,
      "screenshots": [
        {
          "index": 0,
          "name": "Seq_Starfall_0000",
          "image": "Screenshot/1/Seq_Starfall_0000.png"
        }
      ]
    }
  ],
  "artifacts": {
    "map_build_data": {
      "path": "Artifacts/MapBuildData/map_build_data.json",
      "format": "map-build-data/v2",
      "status": "complete"
    }
  }
}
```

v2 不变量：

- 同一批次的 `shading_quality` 最多出现一次；`quality_run_index` 也必须唯一且为非负整数。
- 每个画质运行必须是 `status: "complete"`，必须有至少一张截图，`screenshot_count` 必须等于数组长度，同一运行内 `name` 不得重复。
- 若提供 `ue_data.tex_quality_levels`，其顺序和值必须与 `quality_runs[].tex_quality` 完全一致。
- 路径必须是使用 `/` 的安全相对路径；不接受绝对路径、反斜杠、空路径和 `..`。
- 纯烘培包可以省略 `quality_runs` 或使用空数组；采集阶段部分失败的画质运行不应上报。

下面的 `format_version: 1` 结构仅用于兼容旧采集端；后端和当前上报客户端会把它转换成单个画质运行。

```text
<批次目录>/
  manifest.json
  Screenshot/
    01_广场.png
    02_街道.png
  Artifacts/
    MapBuildData/
      map_build_data.json
```

manifest 示例：

```json
{

  "pipeline_data": {
    "id": "20260710_001",
    "branch_tag": "main",

```

兼容字段：

- `pipeline_data.id` 也可写为 `pipeline_data.batch_id`。
- `pipeline_data.url` 也可写为 `pipeline_data.batch_url`。
- `pipeline_data.branch_tag` 省略时归入 `main`；分支会去除首尾空格并转成小写。
- `pipeline_data` 整体可省略；批次 ID 由后端生成，分支使用 `main`，创建时间使用入库时间。
- `screenshots` 可以省略或为空；`artifacts.map_build_data` 也缺失时只创建“待补传”批次。浏览器手动上报为避免误选空目录，仍要求截图或烘培数据至少存在一种。

## 3. 创建批次

```http
POST /api/batches
Content-Type: application/json
```

请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | string | 否 | 批次 ID；省略时取现有纯数字 ID 最大值加一 |
| `branch_tag` | string | 否 | 分支；默认 `main`，只允许小写归一化后的字母、数字、`.`、`_`、`-`、`/`，长度 1–128 |
| `scene_id` | string | 是 | UE Level/World 名；同场景才能比较 |
| `platform` | string | 是 | 平台；WindowsEditor 等会被归一化 |
| `p4_version` | int/null | 否 | P4 changelist，越大越新 |
| `creator` | string | 否 | 默认 `CI机器人` |
| `batch_url` | string/null | 否 | CI/流水线链接 |
| `resolution` | string/null | 否 | 例如 `1920x1080` |
| `capture_type` | string/null | 否 | 例如 `levelsequence` |
| `levelsequence_name` | string/null | 否 | LevelSequence 名称 |
| `levelsequence_path` | string/null | 否 | LevelSequence 资源路径 |
| `shading_quality` | int/null | 否 | 仅旧单画质 API 兼容字段；v2 不发送 |
| `manifest_format_version` | int/null | 否 | 来源 manifest 版本；v2 传 `2` |
| `source_manifest_sha256` | string/null | 否 | 可选的 64 位 manifest SHA-256，便于审计 |
| `quality_runs` | array/null | 否 | v2 画质运行与截图计划；纯烘培包可传空数组，旧客户端可省略 |
| `captured_at` | ISO8601 string | 否 | 采集时间；解析失败时回退到入库时间 |
| `overwrite` | bool | 否 | 同号批次存在时是否删旧建新，默认 `false` |

`quality_runs[]` 字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `quality_run_index` | int | 是 | 批次内唯一的非负运行序号 |
| `shading_quality` | int | 是 | 画质身份 0–5；批次内唯一 |
| `tex_quality` | int/null | 否 | 采集参数，仅保存，不用于筛选和对比身份 |
| `capture_status` | `"complete"` | 是 | 当前协议只接受完整运行 |
| `screenshots` | array | 是 | 至少一项的完整截图计划 |
| `screenshots[].scene_name` | string | 是 | 画质运行内唯一的检查点名 |
| `screenshots[].source_relative_path` | string | 是 | manifest 包内安全相对路径，供审计和槽位匹配 |
| `screenshots[].frame_index` | int/null | 否 | 帧序 |
| `screenshots[].camera` | object/null | 否 | 相机数据 |

画质约定：

| 值 | 显示名 |
|---:|---|
| 0 | 节能 |
| 1 | 流畅 |
| 2 | 均衡 |
| 3 | 精美 |
| 4 | 极致 |
| 5 | 电影 |

历史数据或缺省值按 4（极致）显示。

请求示例：

```bash
curl -X POST http://127.0.0.1:8020/api/batches \
  -H "Content-Type: application/json" \
  -d '{
    "id": "101",
    "branch_tag": "main",
    "scene_id": "Lv_Starfall",
    "platform": "WindowsEditor",
    "p4_version": 251200,
    "manifest_format_version": 2,
    "resolution": "1920x1080",
    "creator": "render-farm-ci",
    "quality_runs": [{
      "quality_run_index": 0,
      "shading_quality": 5,
      "tex_quality": 0,
      "capture_status": "complete",
      "screenshots": [{
        "scene_name": "Seq_Starfall_0000",
        "source_relative_path": "Screenshot/0/Seq_Starfall_0000.png",
        "frame_index": 0
      }]
    }]
  }'
```

成功返回 `201`，响应中的 `id` 是后续上传必须使用的最终批次 ID。

读取批次目录时使用 `GET /api/batches?branch_tag=main`；省略分支仍只返回 `main`，不表示全部分支。批次号全局唯一，需要按 ID 精确读取时使用 `GET /api/batches/{batch_id}`，它不要求额外传分支。响应的 `quality_runs` 给出各档计划数、已就绪数和 `is_complete`，`shading_qualities` 给出声明档位，`available_shading_qualities` 只给出完整可用档位。`has_screenshots`、`has_map_build_data` 由已落库数据实时派生；`scene_count` 按唯一检查点名统计，不会因多个画质重复累加。`GET /api/meta` 的 `branch_tags` 返回已有分支选项，并始终把 `main` 放在首位。

### 重复批次语义

- `overwrite=false`：返回 `409 BATCH_ALREADY_EXISTS`，客户端必须停止，不能合并或继续补传。
- `overwrite=true`：级联删除旧批次、截图、相关对比、对比项、基线关联和派生图片，再创建新批次。
- 覆盖只能重建同一分支、场景和平台的批次；任一范围字段变化返回 `BATCH_BRANCH_IMMUTABLE` 或 `BATCH_SCOPE_IMMUTABLE`。
- 相关对比正在计算时，覆盖返回 409，应稍后重试。
- 批次 ID 在所有分支间全局唯一；已有批次的分支不可修改。使用同一 ID 提交不同 `branch_tag` 会返回 409，不能按普通补传处理。

覆盖是破坏性操作，不应作为普通网络重试策略。生产脚本只允许显式命令行 `--overwrite` 开启；manifest 内的 `pipeline_data.overwrite` 或顶层 `overwrite` 不会授权覆盖。

## 4. 上传截图

```http
POST /api/batches/{batch_id}/quality-runs/{shading_quality}/screenshots?branch_tag=main
Content-Type: multipart/form-data
```

新版接口只能写入创建批次时已声明的 `(batch_id, shading_quality, scene_name)` 槽位。旧的 `POST /api/batches/{batch_id}/screenshots` 仅兼容可唯一确定单个画质运行的旧客户端；多画质批次调用旧接口会返回 `422 AMBIGUOUS_QUALITY_RUN`。

字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `scene_name` | text | 是 | 检查点唯一配对键 |
| `file` | file | 是 | 截图文件，当前约定使用 PNG |
| `camera` | JSON string | 否 | 相机位置和旋转 |
| `frame_index` | int | 否 | 帧序 |

示例：

```bash
curl -X POST 'http://127.0.0.1:8020/api/batches/101/quality-runs/5/screenshots?branch_tag=main' \
  -F "scene_name=01_废弃都市_广场_昼" \
  -F "frame_index=0" \
  -F 'camera={"location":{"x":1,"y":2,"z":3},"rotation":{"pitch":0,"yaw":90,"roll":0}}' \
  -F "file=@Screenshot/01_废弃都市_广场_昼.png;type=image/png"
```

首次成功返回 `201`。相同槽位用完全相同的图片内容重试返回 `200` 且 `idempotent: true`；不同内容重试返回 `409 SCREENSHOT_CONTENT_CONFLICT`，必须检查采集包或使用整批覆盖。常见失败：

- 404：批次不存在。
- 400：`scene_name` 是空值、`.`、`..`，或包含路径分隔符。
- 409：槽位内容冲突，或请求分支与批次所属分支不一致。
- 413：单图超过 `PIXELCOMP_MAX_SCREENSHOT_BYTES`，默认 100 MiB。
- 422：画质运行不存在、尚未能唯一解析画质或表单不合法。

服务端以 1 MiB 块流式写入临时文件并计算 SHA-256，不会把整张图先读入内存；通过大小校验后原子发布到 `images/batches/<batch>/<quality>/`。采集端仍应确保内容是可解码 PNG，并在反向代理层配置与应用上限一致的请求体限制。

### 检查点命名建议

建议只使用中文、英文字母、数字、下划线和短横线，例如：

```text
01_废弃都市_广场_昼
SeqVillage_Frame0001
```

同一检查点在所有版本中必须保持完全相同的名字，否则会被识别为新增和缺失，而不是同一张图的差异。

## 5. 上传烘培数据

电影档批次可以随附一份 `map-build-data/v2` JSON。先创建批次并取得最终 ID，然后把文件内容作为请求体直接提交：

```http
POST /api/batches/{batch_id}/map-build-data?branch_tag=main&format=map-build-data%2Fv2
Content-Type: application/json
```

```bash
curl -X POST 'http://127.0.0.1:8020/api/batches/101/map-build-data?branch_tag=main&format=map-build-data%2Fv2' \
  -H 'Content-Type: application/json' \
  --data-binary @Artifacts/MapBuildData/map_build_data.json
```

顶层结构：

```json

          "lightmapTextures": { "residentBytes": "1000000", "allMipsBytes": "1000000", "cookEstimateBytes": "800000" },

```

当前 UE 产物把 64 位字节数编码为十进制字符串，后端也兼容 JSON 整数。所有数值必须非负且不超过 SQLite 64 位整数范围；`path` 在单批次内唯一，`blockIndex/subBlockIndex` 坐标不能重复，子分块必须带所属分块索引，单批最多 5000 个 Registry。违反约束返回 `422`，不会写入半份数据。

```json
{
  "batch_id": "101",
  "scene_id": "Lv_Starfall",
  "format": "map-build-data/v2",
  "registry_count": 70,
  "updated": false
}
```

接口按内容幂等：第一次上报 `updated=false`；完全相同的 `format` 和规范化 payload 重试返回 `idempotent=true`，不重复写行。相同批次提交不同内容返回 `409 MAP_BUILD_CONTENT_CONFLICT`，必须回到批次创建阶段显式整批覆盖，不能单独替换烘培快照。删除或覆盖批次时，烘培数据一起级联删除。

后端同时保留完整 JSON 和常用指标索引。页面查询接口为：

```http
GET /api/map-build/meta?branch_tag=main
GET /api/map-build/scenes/{scene_id}/overview?branch_tag=main&batch_id=101
GET /api/map-build/scenes/{scene_id}/trend?branch_tag=main&block_index=3&metric_scope=self&days=30
GET /api/map-build/scenes/{scene_id}/trend?branch_tag=main&registry_path=%2FGame%2FMaps%2Fmain%2FCoralWP%2FCoral_WP_BuiltData_BlockRefl.Coral_WP_BuiltData_BlockRefl&days=30
GET /api/map-build/scenes/{scene_id}/trend?branch_tag=main&start_date=2026-06-01&end_date=2026-06-30
```

`overview` 返回指定或最新批次的独立主分块/分块/子分块网格，不查询上一批次，也不返回增量；省略 `batch_id` 即取最新。`world.path`、`blocks[].path` 和 `sub_blocks[].path` 分别给出对应 Registry 路径，拓扑不完整时前两者可能为 `null`。每个节点的 `self_metrics` 表示节点自身，`subtree_metrics` 表示节点自身与全部后代的汇总，`has_children` 表示是否可切换口径；兼容字段 `metrics` 仍指向 `subtree_metrics`。概览除总 Mip 与 Cook 估算外，还会把上述 breakdown 资源项展开为稳定的 snake_case 指标；旧上报缺少可选资源项时按 0 处理。

`trend` 省略索引和路径时查主分块，只传 `block_index` 时查对应数字分块，同时传两个索引时查子分块。`BlockRefl` 等没有数字索引的直属节点使用概览响应中返回的完整 `path` 作为 `registry_path`；它不能与 `block_index` 或 `sub_block_index` 同时使用。`metric_scope=self` 是默认口径，`metric_scope=subtree` 返回含子级汇总；`days` 范围为 1～365，时间窗口以场景最新快照日期为结束日。也可以同时传递 `start_date` 和 `end_date` 查询包含首尾日期的自定义范围，此范围最多 90 天；自定义日期存在时忽略 `days`。一天内多个批次都会保留并按时间、批次 ID 排序；单次最多返回最新 2000 个点，超过时响应的 `window.truncated` 为 `true`。前端不按平台和画质筛选；接口仍兼容可选的 `platform` 与 `shading_quality` 参数，供外部程序需要限定产出条件时使用。

## 6. 自动选择参照批次

全部截图上传成功后调用；纯烘培批次不能调用：

```http
POST /api/batches/{batch_id}/auto-compare
```

选择范围是同 `branch_tag`、同 `scene_id`、同归一化平台、同画质，并且包含截图的历史批次。

选择顺序：

1. 当前批次有 P4 版本时，优先选择更小且最接近的 P4 版本。
2. 没有更小版本时，在相同 P4 中选择创建时间更早且最近的批次。
3. 当前批次没有 P4 时，按创建时间选择更早且最近的批次。

找到参照：

```json
{
  "matched": true,
  "ref_batch_id": "100",
  "task_id": "...",
  "status": "running"
}
```

没有参照：

```json
{
  "matched": false
}
```

找到已有缓存时，响应也可能直接包含 `status: "done"` 和 `comparison`。

## 7. 手动发起对比

```http
POST /api/comparisons
Content-Type: application/json
```

```json
{
  "batch_id": "101",
  "ref_batch_id": "100",
  "force": false
}
```

规则：

- 两个 ID 不能相同。
- 两个批次必须有相同 `branch_tag` 和 `scene_id`，且两侧都包含截图；平台可不同。
- 同一无方向批次对只保存一条结果。
- 已有结果且 `force=false` 时直接返回缓存。
- `force=true` 强制重新计算。

新任务返回：

```json
{
  "task_id": "e3f...",
  "status": "running",
  "done": 0,
  "total": 0,
  "flip": false
}
```

轮询：

```http
GET /api/comparisons/tasks/{task_id}
```

运行中：

```json
{
  "status": "running",
  "done": 4,
  "total": 12
}
```

完成后响应包含 `comparison`。失败时状态为 `error`。

任务进度只保存在当前后端进程内存中。客户端应设置合理的总超时和网络重试，但不能把 404 的旧 task ID 当作成功；服务重启后需要重新查询或重新发起对比。

## 8. 查询已有对比

只检查缓存、不触发计算：

```http
GET /api/comparisons/lookup?batch_id=101&ref_batch_id=100
```

该接口忽略方向，返回已有 comparison 及按 `scene_name` 索引的热力图 URL。`status` 明确区分 `missing`、`running` 和 `done`，并同时返回 `ready`、`task_id`、`done` 与 `total`。截图对比工作区据此决定显示“发起对比”、恢复任务轮询或展示热力图；服务异常退出留下的空记录会表现为 `missing`，重新发起时复用记录并计算，不会误报完成。

以下历史与详情接口继续保留给外部调用方，当前前端不再提供独立的历史或详情页面。

对比列表：

```http
GET /api/comparisons?branch_tag=main
```

对比检查点：

```http
GET /api/comparisons/{comparison_id}/scenes?page=1&page_size=20&sort=diff&q=广场
```

单个检查点详情：

```http
GET /api/items/{item_id}
```

## 10. 浏览器手动上报

不需要编写客户端时，可以从前端顶栏打开手动上报：

1. 拖入数据包目录；数据包可包含截图、烘培数据或两者。
2. 检查解析后的批次信息、全部画质档位、截图数量和 Registry 数量；重复画质、运行不完整、计数不一致或缺图不会进入预览。
3. 必要时填写 P4 版本、选择是否覆盖和是否自动对比。
4. 原子创建画质计划并开始上传；每张图写到对应画质接口，纯烘培包不会触发图片自动对比。

浏览器上报适合人工联调。已存在的批次不能合并或补传，只有勾选覆盖并二次确认后才能整批重建。稳定 CI 应使用生产上报脚本或直接调用 API，并记录批次 ID、每档完成度、每张图片结果和最终 task ID。

## 11. 仓库参考脚本

`mock_uploads/upload.py` 是标准库实现的演示脚本，用于上传仓库自带示例包：

```powershell
python mock_uploads\upload.py
python mock_uploads\upload.py 7
$env:BASE = "http://127.0.0.1:8020"
python mock_uploads\upload.py 7 8
```

它会识别 manifest 中的 `artifacts.map_build_data`，展示 JSON 请求和 multipart 拼装，但不是完整生产客户端：没有完善的网络重试、上传汇总退出码、任务等待或质量门禁。生产采集端可以参考其字段映射，不应直接依赖其控制台输出判断 CI 成败。

仓库当前没有独立的根目录 `report.py`。

ArashiTestCase 集成使用 `Cases/Heatmap/PixelComparisonReport.py`。它兼容 v1/v2 manifest，默认并发流式上传 4 张截图（`--upload-workers 1..8` 或 `PIXELCOMP_UPLOAD_WORKERS`），支持 `--branch_tag`、`--no-auto-compare` 和显式 `--overwrite`。示例：

```powershell
python Cases\Heatmap\PixelComparisonReport.py C:\data\PixelComparison --base http://127.0.0.1:8020
python Cases\Heatmap\PixelComparisonReport.py C:\data\PixelComparison --branch_tag engine-ue5 --upload-workers 4
python Cases\Heatmap\PixelComparisonReport.py C:\data\PixelComparison --overwrite
```

manifest 内的 `overwrite` 字段不会打开覆盖权限；必须由操作者传 `--overwrite`。脚本先完整校验画质、运行序号、计数、状态和路径，再原子建计划；截图采用 1 MiB 块流式传输，网络错误和 5xx 有限重试，相同内容重试由服务端哈希幂等处理。

## 12. 同步前端场景目录

外部模块可以下发一份权威场景目录，同时控制批次页“场景 ID”筛选框的内容和从上到下的顺序。接口采用全量替换语义，重复发送相同内容结果不变：

```http
PUT /api/scene-catalog
Content-Type: application/json
```

```json
{
  "scene_id_order": [
    "Village_Dimension_Main",
    "RottenVale_WP",
    "OtherScene"
  ]
}
```

请求示例：

```bash
curl -X PUT http://127.0.0.1:8020/api/scene-catalog \
  -H 'Content-Type: application/json' \
  -d '{"scene_id_order":["Village_Dimension_Main","RottenVale_WP","OtherScene"]}'
```

规则：

- 数组顺序就是筛选框顺序，每次请求完整覆盖上一次目录。
- 目录中的场景即使数据库中还没有任何批次，也会出现在筛选框；选择后显示空数据。
- 数据库中存在、但本次目录没有包含的场景不会删除数据，只会默认从筛选框隐藏。
- 项目设置开启“目录外场景”后，未列入目录但数据库中存在的场景按名称排序追加到末尾，并标记为“未配置”。
- 空数组是合法的，表示默认隐藏全部数据库场景；开启“目录外场景”后仍可查看它们。
- 场景 ID 必须非空、不能有首尾空格、不能重复，单项最长 255 个字符，列表最多 5000 项；违反约束返回 `422`，原目录保持不变。
- 当前打开的前端会在手动刷新、切回浏览器前台或最多一分钟的自动刷新后取得新目录。当前选中场景被隐藏时，筛选会自动清空。

读取当前权威目录：

```http
GET /api/scene-catalog
```

未曾同步时返回 `configured: false` 和 `scene_id_order: null`，前端保持兼容，按名称显示数据库中的全部场景。同步空数组后则返回 `configured: true` 和空列表，两种状态含义不同。

该接口会修改所有用户共享的项目级配置。当前项目没有身份认证，只应在可信内网中向受信任模块开放；多个模块同时写入时以最后一次成功请求为准。

## 13. 生产客户端建议

推荐实现以下行为：

1. 创建任何服务端数据前验证 v2 的画质唯一性、运行序号唯一性、`complete` 状态、截图计数、检查点名和安全路径；截图和烘培数据都缺失时只创建诊断批次且不触发自动对比。
2. 为创建批次、烘培快照、每张截图和自动对比记录结构化日志。
3. 连接失败和 5xx 使用有限次数的指数退避。
4. 409 按错误码区分：批次存在必须停止或由操作者显式整批覆盖；截图相同内容重试会返回 200，截图内容冲突和烘培内容冲突必须停止；分支冲突必须停止；覆盖被运行中任务阻止时可稍后重试。
5. 对批次 ID 和 `scene_name` 做明确字符约束。
6. 设置请求超时和单图/总包大小限制；图片使用流式传输，不要一次读入内存。
7. manifest 声明烘培数据时校验文件存在，并按相同批次 ID 幂等重试。
8. 创建批次和所有写入接口都传递同一个归一化 `branch_tag`；批次 ID 在全局生成，不能按分支重复。
9. 只有数据包包含截图且所有画质计划完整后才调用自动对比；服务端会为每档画质分别寻找同画质历史参照。
10. 若 CI 需要视觉质量门禁，轮询任务直到完成，并根据 pass/warn/fail 设计明确退出码。

## 14. 状态码速查

| 状态码 | 典型含义 |
|---:|---|
| 200 | 查询成功、命中已有结果，或相同截图内容幂等重试成功 |
| 201 | 批次、截图或首份烘培快照创建成功 |
| 202 | 对比任务已接受或自动对比请求已处理 |
| 204 | 客户端日志接收成功 |
| 400 | 参数非法、自比较、场景不一致、分支不一致或批次缺少截图 |
| 404 | 批次、任务、对比项或文件不存在 |
| 409 | 批次已存在、截图/烘培内容冲突、分支不匹配，或计算中的对象不能删除/覆盖 |
| 413 | 单张截图超过服务端大小上限 |
| 422 | manifest 计划、画质解析、JSON、表单或参数不符合约束 |
| 500 | 服务端异常；客户端可有限重试并保留请求上下文 |

新版写入错误响应保留兼容的 `detail`，同时提供稳定字段：

```json
{
  "detail": "batch 101 already exists",
  "code": "BATCH_ALREADY_EXISTS",
  "message": "batch 101 already exists"
}
```

生产客户端至少应识别 `BATCH_ALREADY_EXISTS`、`BATCH_BRANCH_IMMUTABLE`、`BATCH_SCOPE_IMMUTABLE`、`DUPLICATE_SHADING_QUALITY`、`DUPLICATE_QUALITY_RUN_INDEX`、`AMBIGUOUS_QUALITY_RUN`、`QUALITY_RUN_NOT_FOUND`、`QUALITY_RUN_INCOMPLETE`、`SCREENSHOT_CONTENT_CONFLICT`、`SCREENSHOT_TOO_LARGE` 和 `MAP_BUILD_CONTENT_CONFLICT`；未知错误码按 HTTP 状态回退处理。

## 15. 数据保留

- 原始批次和截图不会按时间自动删除，需要人工删除或使用维护脚本。
- 分支标签、数据能力和烘培快照保存在 SQLite 中并跟随批次生命周期，不受对比结果 14 天保留期影响。
- 对比结果默认保留 14 天，在后续对比创建或完成时淘汰。
- 截图上报成功后会异步预生成缩略图，不阻塞上传；缩略图是可重建缓存，默认按 60 天未访问淘汰。
- SQLite 数据库每天自动备份，默认保留 30 天。
- 数据库备份不包含截图文件；图片需要独立备份策略。

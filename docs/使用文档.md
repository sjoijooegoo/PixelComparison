# PixelComparison 使用文档

本文面向日常使用者和项目维护者，说明如何启动系统、浏览批次、发起对比、调整算法、管理数据以及恢复数据库。采集端和 CI 的接口细节见[数据上报接入指南](上报接入指南.md)。

## 1. 启动与访问

### 1.1 默认地址

开发模式：

| 服务 | 地址 |
|---|---|
| 前端页面 | http://127.0.0.1:5173 |
| 后端 API | http://127.0.0.1:8020 |
| OpenAPI/Swagger | http://127.0.0.1:8020/docs |

生产式单端口模式默认使用 http://127.0.0.1:8800。

### 1.2 Windows 一键启动

首次准备依赖：

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
cd ..\frontend
npm ci
cd ..
```

开发启动：

```powershell
.\run-dev.ps1
```

脚本会打开后端和前端两个控制台。默认数据目录固定为当前项目的 `backend\data`，不会根据其他盘符自动切换。

可选参数：

```powershell
.\run-dev.ps1 -BackendPort 8020 -DataDir "D:\PixelComparisonData"
```

通用双进程启动：

```powershell
.\run.ps1
```

生产式单端口启动：

```powershell
.\run-prod.ps1
.\run-prod.ps1 -Port 9000
.\run-prod.ps1 -SkipBuild
```

### 1.3 手动启动

后端：

```powershell
cd backend
.\.venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8020 --reload
```

前端：

```powershell
cd frontend
npm run dev
```

Vite 默认代理到 8020。使用其他后端端口时，启动前设置：

```powershell
$env:PIXELCOMP_BACKEND_URL = "http://127.0.0.1:9000"
npm run dev
```

### 1.4 Linux 部署与更新

以下示例使用本地 SQLite 和缩略图缓存，原图、热力图、日志及日备份使用远端大容量目录：

```bash
cd /data/workspace/PixelComparison
git fetch origin
git switch woa-master
git pull --ff-only origin woa-master

export PIXELCOMP_DATA_DIR=/agentdrive/v_sycisong/PixelComparison
export PIXELCOMP_DB_PATH=/data/workspace/PixelComparison/backend/data/shotdiff.db
export PIXELCOMP_IMAGES_DIR=/agentdrive/v_sycisong/PixelComparison/images
export PIXELCOMP_THUMB_DIR=/data/workspace/PixelComparison/backend/data/thumbs

mkdir -p "$(dirname "$PIXELCOMP_DB_PATH")" "$PIXELCOMP_IMAGES_DIR" "$PIXELCOMP_THUMB_DIR"

cd backend
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8020
```

首次用本版本启动旧数据库时，后端会在监听端口前执行多画质 schema v2 迁移：先用 SQLite 在线备份 API 在 `backup/<日期>/db/` 生成带 `pre-multi-quality-v2` 标记的迁移前快照并校验，再重建截图关联、为旧批次回填单个 legacy 画质运行，最后执行 `PRAGMA quick_check`。迁移失败会终止启动，不会带着半迁移数据库继续服务。发布时应先停旧后端、保留主库和图片目录，再启动新版本；不要同时运行新旧两个后端进程。

如果 `git pull` 提示 `You are not currently on a branch`，说明当前处于 detached HEAD，先执行 `git switch woa-master`。本地还没有该分支时执行：

```bash
git fetch origin
git switch -c woa-master --track origin/woa-master
```

需要使用 8021 时，只修改后端端口，并让 Vite 指向相同端口：

```bash
# 后端终端
python -m uvicorn app.main:app --host 0.0.0.0 --port 8021

# 前端终端
cd /data/workspace/PixelComparison/frontend
export PIXELCOMP_BACKEND_URL=http://127.0.0.1:8021
npm run dev -- --host 0.0.0.0
```

tmux 新窗口不会自动继承之后在其他窗口修改的变量。需要长期生效时，将四条 `export` 写入 `~/.bashrc`，然后在启动后端的 tmux 窗口执行：

```bash
source ~/.bashrc
```

## 2. 核心概念

| 名称 | 含义 |
|---|---|
| 分支 | 批次所属的代码/资源分支，对应 `branch_tag`；旧数据和未填写的上报属于 `main` |
| 场景 ID | 批次所属的 UE Level，对应 `scene_id`；只有相同场景 ID 的批次能比较 |
| 批次 | 一次采集运行，包含分支、场景、平台、一个或多个画质运行、P4 版本，以及截图和/或烘培数据 |
| 画质运行 | 批次内一个 `shading_quality` 的完整截图集合；同一批次同一画质最多出现一次，`tex_quality` 只保存为采集参数 |
| 数据能力 | 由真实数据派生的“截图”“烘培”“截图 · 烘培”或“待补传”状态 |
| 检查点 | 批次内的一张截图，对应 `scene_name`；不同批次按该名字配对 |
| 基线批次 | 用户选择的参照侧；不要求数据库中已经存在 Baseline 记录 |
| 对比批次 | 待检查的当前侧 |
| 对比 | 一对批次的持久化比较结果；正反方向只保存一条记录 |
| 对比项 | 单个检查点的状态、指标、两侧图片和热力图 |
| 烘培快照 | 一个批次随附的一份 `map_build_data`；保存主分块、分块和子分块的体积指标 |

检查点状态：

| 状态 | 判定 |
|---|---|
| `pass` | 差异率低于警告阈值 |
| `warn` | 差异率达到警告阈值但低于失败阈值 |
| `fail` | 差异率达到失败阈值 |
| `added` | 仅对比批次存在该检查点 |
| `missing` | 仅基线批次存在该检查点 |

默认警告阈值是 0.3%，默认失败阈值是 2.0%。项目设置可修改阈值。

## 3. 页面导航

| 页面 | URL | 用途 |
|---|---|---|
| 批次管理 | `/batches?...` | 按分支筛选、预览和维护全部批次；筛选与页码可从 URL 恢复 |
| 截图对比 | `/screenshot/:sceneId?` | 多版本截图网格、基线/对比选择和差异热力图 |
| 旧列表图链接 | `/batches/:sceneId` | 自动重定向到同场景的截图对比 |
| 烘培数据 | `/map-build/:sceneId?branch_tag=main` | 查看指定分支与场景的最新烘培数据、分块细则和趋势 |
| 项目设置 | `/settings` | 调整算法和默认筛选 |

顶栏提供页面切换、当前页面刷新、手动上报和主题切换。批次管理、截图对比和烘培数据都会在右上角显示刷新与手动上报按钮，并每 60 秒静默刷新当前活动页面；浏览器标签重新回到前台时也会立即刷新。旧 `/comparison` 和 `/comparison/:id` 不再提供前端页面，会进入批次管理。

## 4. 批次管理

### 4.1 筛选

顶部筛选条包含：

- 分支：默认 `main`，选项来自已经上报的批次；不提供“全部分支”。
- 场景 ID：可搜索和清空。
- 创建时间：连续范围最多选择14个自然日；需要跨越更长时间时，可使用“指定日期”选择多个离散日期。
- 清空：恢复 `main` 分支、全部场景及项目设置中定义的默认日期范围。

批次管理的分支、场景、日期和页码会写入 URL，不按画质筛选。例如：

```text
/batches?branch_tag=main&scene_id=Coral_WP&date_mode=range&from=2026-08-07&to=2026-08-20&page=2
```

F5、复制链接及浏览器前进/后退都会恢复对应状态；无参数 `/batches` 默认使用 `main` 和全部场景。历史链接中的 `quality` 参数会被忽略并从地址中清理；其他非法参数会回退默认并规范化地址。动态 `page_size` 只取决于当前窗口高度，不写入 URL。批次管理状态不会修改截图对比的筛选、角色或网格位置；切换分支、场景或日期时回到第一页。

如果外部模块已经同步权威场景目录，场景 ID 下拉框会严格按目录顺序显示。目录中尚无批次的场景仍会显示；数据库中存在但未列入目录的场景默认隐藏。

批次列表按批次号的数值降序显示，最新批次通常位于最前。

### 4.2 批次表格

列表展示批次 ID、分支、场景 ID、平台、画质、P4 版本、检查点数量、数据能力和创建时间。一个批次有多个画质运行时，“画质”列同时展示全部档位；检查点数量按唯一名称统计，不会因多画质重复累加。批次可以只有截图、只有烘培数据、两者都有，或处于创建后尚未补传数据的状态。

每行支持：

- 预览：打开该批次的截图画廊。默认选择电影画质（5）；没有电影档时选择已完整上传的最高画质。弹窗顶部可切换该批次的其他完整画质。画廊卡片只加载 WebP 缩略图，点击某张图片进入灯箱时才加载对应原图。
- 删除：二次确认后级联删除批次、截图、相关对比、对比项、基线关联和派生图片。
- 查看烘培数据：每行始终显示；拥有烘培快照时可直接打开相同分支、场景和批次的烘培页面，没有烘培数据时按钮置灰。

没有截图的批次不能预览，但仍会完整显示在批次表格中；有烘培数据时可以进入烘培页面。批次表格不再提供截图对比行操作。

### 4.3 截图对比工作区

点击顶栏“截图对比”进入空工作区，再选择场景和批次。标准可分享地址如下：

```text
/screenshot/Coral_WP?branch_tag=main&quality=4&date_mode=range&from=2026-08-06&to=2026-08-19&baseline=1238&current=1241
```

`branch_tag`、场景 ID、画质、日期、基线批次和对比批次均由 URL 恢复。`quality=all` 表示全部画质；指定日期模式使用 `date_mode=days&dates=2026-08-01,2026-08-03`。切换分支或场景会继承当前画质和日期，修改画质或日期使用地址替换，并清除当前基线/对比选择，不会为每次筛选制造浏览器历史。旧链接缺少筛选参数时使用项目默认值并自动补全地址；非法日期或画质也会回退默认并规范化 URL。

非法、已删除、无截图、跨分支、跨场景、重复或不在当前筛选结果内的角色参数会被自动清理。URL 中的画质和日期筛选始终优先；刷新页面只恢复当前筛选内可见的基线和对比角色，不会自动切换为“指定日期”。截图对比筛选独立于批次管理，不在两个页面之间互相覆盖。

布局规则：

- 每列代表一个“批次 + 画质”组合，左旧右新；选择“全部画质”时，同一批次可展开为多列。
- 只显示当前分支、当前场景中包含截图的批次；批次管理仍显示纯烘培批次。
- 每行代表一个检查点。
- 缺少截图的格子显示占位符。
- 最右侧固定为差异热力图列。

当前筛选没有包含截图的批次时，页面显示“当前分支和场景下没有包含截图的批次”，不会用纯烘培批次生成空图片列。

交互：

- 列头可以折叠和展开单个批次。
- 点击列头角色按钮选择基线或对比列，再点一次取消；两侧画质不同的列不能组成对比。
- 角色写入 URL，刷新、复制链接及浏览器前进/后退均可恢复。
- 按住图片矩阵拖动可横向和纵向平移。
- 点击缩略图打开大图。
- 大图中使用 `←`、`→` 跨批次，使用 `↑`、`↓` 跨检查点，按 `Esc` 关闭。

选择两个批次后：

- 已有对比时，热力图列直接显示缓存，不重新计算。
- 没有结果时，热力图列表头显示“发起对比”。计算在当前页面进行，完成后填充热力图，不跳转。
- 已有结果时可以点低调的“重新对比”强制重算；点击单张热力图只打开热力图大图。
- 离开页面只会停止当前浏览器轮询，不会中止后端任务；重新进入并选择同一批次对会恢复进度或最终热力图。

快速切换分支、场景、日期、画质或角色时，前端会取消已经失效的网格、批次元数据、热力图和任务轮询；相同参数的并发请求会复用同一个在途请求，晚到的旧响应不会覆盖当前界面。

当前截图网格会构造完整二维矩阵，批次和检查点很多时请求数较高。二维虚拟化仍是待办项。接口生成图片 URL 时使用数据库缓存版本，不会对共享盘中的每张原图执行文件状态查询；覆盖批次或强制重算后缓存版本会自动变化。

## 5. 手动上报

在批次管理、截图对比或烘培数据页面点击顶栏上报按钮，把包含 `manifest.json` 的数据包目录拖入弹窗，也可以点击选择目录。

典型结构：

```text
  PixelComparison/
  manifest.json
  Screenshot/
    0/
      01_广场.png
    1/
      01_广场.png
  Artifacts/
    MapBuildData/
      map_build_data.json
```

流程：

1. 浏览器读取并校验 manifest 中的分支、场景、平台、`quality_runs`、完整截图清单和 `artifacts.map_build_data`；重复画质、重复运行序号、非 `complete` 运行、计数不一致或缺图会在创建批次前拒绝。
2. 展示批次元数据、画质档位、可用截图和 Registry 数量。
3. 数据包未提供 P4 版本时，可在弹窗中手动填写。
4. 原子创建批次、全部画质运行和截图计划，上传烘培数据（存在时），再把每张图写入对应画质槽位。
5. 存在截图时，默认在全部截图上传成功后为每个完整画质分别请求同画质自动对比；纯烘培数据包不会请求图片对比。

数据包必须至少包含一张可上传截图或一份有效烘培 JSON。纯烘培数据包可以完全省略 `screenshots`。分支写在 `pipeline_data.branch_tag`，缺省为 `main`；批次 ID 在所有分支间全局唯一，且创建后不能改变分支。

批次 ID 已存在时不会合并或补传：未勾选覆盖不能开始上报；勾选覆盖并二次确认后，先级联删除旧批次数据，再按本次 manifest 整批重建。

覆盖不可恢复，并会删除该批次参与的历史对比和热力图。执行前应确认批次不是他人正在查看或计算的版本。

完整 manifest 和接口说明见[上报接入指南](上报接入指南.md)。

## 6. 对比记录与保留规则

前端不再提供独立的对比历史、结果汇总、检查点状态或指标详情页面。对比记录、检查点指标和热力图仍由后端持久化，用于截图对比工作区复用：重新选择同一对批次时，页面会通过只读 lookup 恢复已有热力图；记录不存在或已过期时才显示“发起对比”。

对比记录继续按现有规则保留 14 天。过期记录不是由固定定时任务删除，而是在后续创建或完成对比时淘汰，相关热力图随后清理。原始批次仍存在时可以重新选择并计算。

后端仍保存差异率、SSIM、PSNR、通道差异和直方图等指标，并保留历史与详情 API 以兼容已有调用方；当前前端不展示这些汇总和指标。两张图分辨率不同时，后端会把基线图缩放到对比图尺寸后计算。

## 7. 烘培数据

顶栏“烘培数据”面向场景烘培产物的体积回归。数据先按分支隔离；场景下拉框与“批次管理”使用同一份项目场景目录、排列顺序和“未配置”标记。尚未上报 `map_build_data` 的场景名称显示为灰色，但仍可选择，页面会显示无烘培数据提示。批次管理根据当前分支和创建时间筛选（范围或指定日期）内是否存在匹配批次来置灰。截图对比使用自身的分支、场景、画质和日期筛选，只有存在完整截图的场景才显示为可用。灰色场景仍可选择，当前已选场景不会因筛选变化而被自动切换。烘培数据页面不按平台和画质筛选，场景置灰也不受趋势日期范围影响，直接按分支、场景与批次查看。地址栏会同步分支和场景，例如 `/map-build/Coral_WP?branch_tag=engine-ue5` 可直接打开该分支 `Coral_WP` 的最新烘培批次。

顶部筛选项：

- 分支：默认 `main`，切换后选择目标分支的最新烘培批次。
- 场景 ID：选择要分析的 UE World。
- 网格批次：决定下方分块网格展示哪一批，默认是最新批次，最多列出最近 100 批。

刷新与手动上报统一放在页面右上角顶栏。点击刷新会重新获取当前场景的批次元数据、分块网格与趋势数据；筛选卡内只保留场景和网格批次选择，避免出现两个含义相同的刷新入口。

页面先展示分块网格，再展示“数据趋势”。顶部的“主分块”是场景烘培 Registry 树的根节点。存在分块树时，网格卡片底部的“仅自身 / 含子级”统计口径统一控制全部有层级的节点标题、右侧细则和下方趋势；“仅自身”只展示直接归属于当前节点的数据，切换为“含子级”后展示当前节点与全部后代的汇总。选择其他节点或批次时会保持当前口径，切换场景时恢复“仅自身”。普通场景没有任何下级节点时，网格中央提示“该场景没有分块数据，仅展示主分块数据”，并隐藏无实际意义的统计口径切换。趋势可查看最近 7、14、30、60 或 90 天，也可以选择“自定义”后在日历中指定一个最多 90 天的闭区间：

| 曲线 | 含义 |
|---|---|
| 总 Mip | 当前节点口径的全部 Mip 规模 |
| Cook 估算 | 当前节点口径的 Cook 体积估算 |
| 光照贴图纹理 | 静态解析得到的光照贴图全 Mip 规模 |
| 阴影贴图纹理 | 静态解析得到的阴影贴图全 Mip 规模 |
| 色相纹理 | 静态解析得到的色相纹理全 Mip 规模 |

预设时间窗口以该场景最新烘培快照所在日期为结束日，并包含结束日；自定义窗口同时包含开始日和结束日。超过 90 天、缺少一端或结束日早于开始日的自定义范围不会发起查询。一天内多次上报会保留为多个独立趋势点，按创建时间和批次 ID 稳定排序；横轴在重复日期旁补充时刻，悬浮提示显示完整时间和批次 ID，不会用后一个批次覆盖前一个。某个历史批次不存在所选分块时，折线会在该点断开，不会把缺失数据伪装成 0。当前批次、节点、统计口径和趋势时间窗口会同步到地址栏，复制链接或刷新页面后可以恢复。图表纵轴统一使用 MiB（`1024 × 1024` 字节）。

趋势图图例同时是指标开关。点击图例可显示或隐藏对应曲线，纵轴量程和悬浮提示会只按当前可见指标计算；页面至少保留一项指标。选择会保存在当前浏览器中，切换场景、分块、时间窗口或刷新页面后继续沿用。

数字分块按 2×2 排列，每个分块内的子格对应一个子分块索引。子格使用节点自身的总 Mip；主分块和所有数字分块标题统一跟随当前“仅自身 / 含子级”口径，包含未选中的节点，右上角标签和值会一起切换为“仅自身”或“含子级汇总”。路径以 `_BlockRefl` 结尾的无索引直属节点显示为“反射分块”：它以紧凑标题卡放在网格左下角，不生成空子网格；同一行右侧保留统计口径按钮。反射分块没有子级，因此卡片只显示名称和自身总 Mip，切换统计口径不会改变它的数值。冷蓝到烘培橙表示当前批次内各子分块的相对总 Mip。本模块不计算或展示上一批次增量。网格统一使用 MiB；小于 `0.001 MiB` 的非零值显示为 `<0.001 MiB`，悬停可查看精确字节数。

分块网格右侧的独立等高详情卡片同步展示主分块、数字分块、反射分块或子分块细则，标题下方显示对应 Registry 的完整路径，并直接跟随网格卡片底部的统计口径。使用“含子级”口径时，有下级的详情标题后会显示“（含子级汇总）”；“仅自身”口径和没有下级的反射分块不显示额外后缀。卡片当前只展示资源规模口径：摘要展示总 Mip、Cook 估算和纹理数；明细按 MiB 从高到低列出光照贴图纹理、阴影贴图纹理、色相纹理、预计算光照/反射体积、体积光照贴图、反射捕获、网格与光照构建数据、预计算实例 ILC/PR 和光照贴图资源簇。采集时驻留数据暂不在界面中展示。

每个批次只保留一份烘培快照。相同批次重复上报会在单个数据库事务中替换旧快照和索引行，不会累积重复数据。完整原始 JSON 会保留以兼容后续字段，常用世界/分块/子分块指标同时规范化存入 SQLite 以便高效查询。升级到包含完整静态趋势指标的版本时，后端首次启动会从原始 JSON 事务性回填旧快照，之后趋势查询无需逐批解析 JSON。烘培历史跟随批次生命周期，不受“对比记录保留 14 天”限制；删除或覆盖批次会一并删除对应烘培快照。

## 8. 项目设置

设置页分为三组。

### 8.1 差异判定

- 像素差异阈值：通道差必须严格大于该值才计为差异像素。
- 红色阈值：整体或检查点达到该差异率时显示失败色。
- 橙色阈值：达到该差异率但未到红色阈值时显示警告色。

橙色阈值不能大于红色阈值。

### 8.2 热力图

- `enhanced`：固定绝对量程、gamma 低端抑制和空间密度门控。
- `legacy`：按单张图片峰值归一化。
- 可调整模糊半径、灵敏度、绝对量程、gamma、密度半径和散点容忍下限。

### 8.3 默认筛选

- 控制截图对比画质下拉中可见的档位。
- 设置截图对比的默认画质，`-1` 表示全部画质；批次管理不按画质筛选。
- 设置默认最近 N 个自然日，范围为1～14天。
- “目录外场景”默认关闭；开启后，把数据库中存在但外部目录未包含的场景追加到场景下拉框，并标记为“未配置”。

设置保存在 SQLite 中。算法参数只影响之后发起或重新计算的对比；筛选设置保存后立即刷新筛选项。当前选中的场景如果因此被隐藏，系统会清空筛选并返回批次列表。

场景目录本身由外部模块通过 `PUT /api/scene-catalog` 全量同步，项目设置页只控制是否显示目录外场景，不手工修改权威目录。接口格式见[上报接入指南](上报接入指南.md#12-同步前端场景目录)。

## 9. 数据目录

默认目录根据项目位置动态计算：

```text
<项目目录>/backend/data/
  shotdiff.db
  shotdiff.db-wal
  shotdiff.db-shm
  images/
    batches/
    heatmaps/
  thumbs/
  backup/
    YYYY-MM-DD/
      db/
        shotdiff.db
  logs/
```

路径配置：

| 变量 | 说明 |
|---|---|
| `PIXELCOMP_DATA_DIR` | 数据、日志和备份根目录 |
| `PIXELCOMP_DB_PATH` | 单独指定 SQLite 文件 |
| `PIXELCOMP_IMAGES_DIR` | 单独指定图片目录 |
| `PIXELCOMP_THUMB_DIR` | 单独指定 WebP 缩略图缓存；默认在数据库文件旁的 `thumbs` 目录 |
| `PIXELCOMP_THUMB_WORKERS` | 后台缩略图生成线程数，默认 `2`，范围 1～8 |
| `PIXELCOMP_THUMB_QUEUE_SIZE` | 缩略图等待队列上限，默认 `64` |

SQLite 主库必须放可靠的本地磁盘。图片目录可以按容量需求放到其他磁盘或共享目录；缩略图缓存应留在本地磁盘。截图上报提交成功后会异步预生成 WebP，不增加上传等待；历史图片或队列遗漏在缓存未命中时会立即回退原图并异步补生成。后台生成线程不会阻止后端退出，但直接访问远程原图仍会受到共享存储延迟影响。

不要在后端运行时手工移动或复制 `shotdiff.db`。WAL 模式下单独复制主文件可能得到不一致数据，应使用自动备份生成的快照。

### 9.1 确认实际生效路径

环境变量为空不代表路径为空；程序会使用表格中的默认值。特别是 `PIXELCOMP_THUMB_DIR` 未设置时，默认取 `PIXELCOMP_DB_PATH` 所在目录下的 `thumbs`。

```bash
cd /data/workspace/PixelComparison/backend
source .venv/bin/activate
python -c "from app.db import DATA_DIR, DB_PATH, IMAGES_DIR, THUMB_DIR; print('DATA_DIR =', DATA_DIR); print('DB_PATH =', DB_PATH); print('IMAGES_DIR =', IMAGES_DIR); print('THUMB_DIR =', THUMB_DIR)"
```

也可检查正在运行进程继承到的显式变量，其中 `<PID>` 替换为后端 PID：

```bash
tr '\0' '\n' < /proc/<PID>/environ | grep '^PIXELCOMP_'
```

### 9.2 缩略图生成和容量维护

缩略图不会在启动时批量创建。新截图完成文件落盘和数据库提交后，上传接口会把 WebP 预生成任务放入后台队列并立即返回，不等待远程读取或编码；正常情况下，用户首次打开截图对比时即可命中本地 WebP。历史图片、服务停止期间的上传以及队列满时遗漏的任务仍由 `/thumb/...` 懒生成兜底：缓存未命中会立即回退原图，同时再次尝试加入后台队列。启动日志应包含 `缩略图后台生成已启用` 和实际缓存目录。

手动触发并确认一次生成，示例中的图片路径应替换为实际存在的截图：

```bash
curl -sS -D - -o /dev/null http://127.0.0.1:8020/thumb/batches/1080/Seq_Volcano_WP_0005.png
sleep 5
find /data/workspace/PixelComparison/backend/data/thumbs -type f -name '*.webp' | head
```

新上报图片等待后台预热完成后，首次响应应直接为 `200 image/webp`；未预热的历史图片首次响应通常为 `307 Temporary Redirect`，后台完成后再次访问会直接返回 WebP。若目录仍为空，检查：

```bash
grep -R -E '缩略图后台生成已启用|缩略图后台生成失败' \
  /data/workspace/PixelComparison/backend/data/logs \
  /agentdrive/v_sycisong/PixelComparison/logs 2>/dev/null | tail -30
```

查看缓存容量和文件数：

```bash
du -sh /data/workspace/PixelComparison/backend/data/thumbs
find /data/workspace/PixelComparison/backend/data/thumbs -type f -name '*.webp' | wc -l
```

当前保留最近 60 天访问过的缩略图，没有固定 GB 上限。命中缓存会刷新访问时间；成功生成新缩略图时最多每 6 小时触发一次过期检查。只预览或执行缩略图清理：

```bash
cd /data/workspace/PixelComparison/backend
source .venv/bin/activate
python -c "from app.cleanup import prune_thumbnails; print('可删除:', prune_thumbnails(dry_run=True))"
python -c "from app.cleanup import prune_thumbnails; print('已删除:', prune_thumbnails())"
```

第二条命令会实际删除超过 60 天未访问的 WebP；原图不会删除，被清理的缩略图会在下次访问时重建。

## 10. 数据库备份与恢复

### 10.1 自动备份

默认目录：

```text
<DATA_DIR>/backup/
  YYYY-MM-DD/
    db/
      shotdiff.db
```

日期使用本地自然日，例如 `2026-07-13/db/shotdiff.db`。如果设置了 `PIXELCOMP_DB_PATH`，备份会保留活动数据库的文件名；例如活动库为 `D:\PixelData\project.db`，当天快照为 `<DATA_DIR>/backup/2026-07-13/db/project.db`。

自动备份只包含 SQLite 数据库。数据库中的 `screenshots.path` 和 `comparison_items.heatmap_path` 只是相对 `PIXELCOMP_IMAGES_DIR` 的路径，图片内容不在数据库中。完整恢复必须保留与数据库快照匹配的 `images/batches` 原图；`images/heatmaps` 可以保留历史热力图，`PIXELCOMP_THUMB_DIR` 中的缓存会按需重建，无需备份。

规则：

- 后端启动时立即检查当天备份。
- 此后默认每小时检查一次。
- 每个自然日只创建一个快照。
- 使用 SQLite 在线备份 API，包含已经提交到 WAL 的数据。
- 临时快照通过 `PRAGMA quick_check` 后原子改名。
- 默认删除 30 天以前的日备份，整个日期目录是保留和删除单元。
- 日期目录由备份系统管理，不要在其中存放人工维护的无关文件；其他工具产生的 SQLite 辅助文件只会留在对应日期的 `db/` 目录内。

环境变量：

| 变量 | 默认 | 说明 |
|---|---:|---|
| `PIXELCOMP_BACKUP_ENABLED` | `1` | `0/false/no/off` 禁用 |
| `PIXELCOMP_BACKUP_RETENTION_DAYS` | `30` | `0` 永久保留 |
| `PIXELCOMP_BACKUP_CHECK_INTERVAL_SECONDS` | `3600` | 检查间隔，最小 60 秒 |

### 10.2 验证备份

在停止后端后，可用 Python 只读检查：

```powershell
@'
import sqlite3
from pathlib import Path
p = Path(r"backend\data\backup\2026-07-13\db\shotdiff.db").resolve()
db = sqlite3.connect(f"{p.as_uri()}?mode=ro&immutable=1", uri=True)
print(db.execute("PRAGMA quick_check").fetchone()[0])
db.close()
'@ | backend\.venv\Scripts\python.exe -
```

输出应为 `ok`。`immutable=1` 会把快照视为不可变文件，避免只读校验在备份目录中创建 `-wal`、`-shm` 或 `-journal` 辅助文件。

### 10.3 恢复备份

恢复会替换当前数据库，必须在后端完全停止后执行。

1. 停止后端，确认 8020/8800 等服务端口不再监听。
2. 对当前 `shotdiff.db` 再做一份人工安全副本。
3. 从选定日期目录复制数据库，例如把 `<DATA_DIR>/backup/2026-07-13/db/shotdiff.db` 复制到 `<DATA_DIR>/shotdiff.db`。
4. 确认 `PIXELCOMP_IMAGES_DIR` 指向与快照匹配的图片目录；至少要保证数据库引用的 `images/batches` 原图存在。现有图片目录中存在未被该快照引用的额外文件不影响恢复。
5. 确认旧进程已经停止后，移走旧的 `shotdiff.db-wal` 和 `shotdiff.db-shm` 辅助文件。
6. 启动后端并检查 `/api/meta`、批次数量、关键原图和历史对比。

如果设置了 `PIXELCOMP_DB_PATH`，应从选定日期的 `db/` 目录取出同名文件，并恢复到该变量指向的活动数据库路径，而不是默认路径。

同盘备份不能应对磁盘整体故障。建议把完整的 `<DATA_DIR>/backup/` 目录树额外同步到异盘或对象存储，以保留日期目录结构和其中的完整快照。原始图片目录建议使用增量或去重备份，避免每天重复复制全部图片。

## 14. 常见问题

### 页面打开但没有数据

先检查后端实际使用的数据目录。默认应为当前项目的 `backend/data`；若设置了 `PIXELCOMP_DATA_DIR` 或 `PIXELCOMP_DB_PATH`，后端可能正在读取另一个库。

```powershell
Get-ChildItem Env:PIXELCOMP_DATA_DIR,Env:PIXELCOMP_DB_PATH -ErrorAction SilentlyContinue
```

### 前端请求 502 或连接失败

确认后端监听 8020，并检查 `PIXELCOMP_BACKEND_URL` 是否指向正确地址。

普通接口超过 30 秒会在前端显示超时，单张图片上传的超时为 120 秒。首次进入页面会先显示加载骨架；失败后可在页面中点击“重新加载”，无需反复 F5。若截图网格持续超时，优先检查后端日志、远程图片目录挂载状态和 8020 反向代理连接，而不是继续扩大前端等待时间。

### 上传返回 409

- 创建批次 409：批次 ID 已存在。
- 上传截图 409：同一批次内该 `scene_name` 已存在。
- 删除或覆盖 409：相关对比可能仍在计算。

### 对比进度在重启后消失

当前任务注册表位于进程内存中。不要在重要对比计算期间重启后端；独立持久化任务队列仍是后续工作。

### 后端收到 Ctrl+C 后长时间不退出

先确认运行的是提交 `b690778` 或更新版本，并把 `PIXELCOMP_THUMB_DIR` 放在本地磁盘。新版本的缩略图生成线程为守护线程，不会阻止 Python 进程退出。升级前遗留的 `<PIXELCOMP_IMAGES_DIR>/thumbs` 仅是可重建缓存，确认没有把它当作原图目录后可以删除。

确认端口和占用进程：

```bash
ss -ltnp 'sport = :8020'
fuser -v 8020/tcp
```

先发送正常退出信号，等待后再检查：

```bash
fuser -TERM 8020/tcp
sleep 3
ss -ltn 'sport = :8020'
```

只有正常退出失败时才强制终止：

```bash
fuser -KILL 8020/tcp
```

`ss -K` 只尝试关闭套接字连接，不能替代终止监听进程。如果 `ss` 显示端口监听但 `fuser` 看不到 PID，应检查进程是否运行在另一个容器、PID/network namespace 或由 systemd 自动拉起，而不是反复启动新的 Uvicorn。

### 备份没有每天出现

检查：

- 后端是否持续运行或当天是否至少启动过一次。
- `PIXELCOMP_BACKUP_ENABLED` 是否被关闭。
- `<DATA_DIR>/logs/backend.log` 中是否有备份失败记录。
- 进程账号是否能创建并写入 `<DATA_DIR>/backup/YYYY-MM-DD/db`。

### 历史对比不见了

对比记录只保留 14 天，并在后续对比创建或完成时清理。原始批次仍存在时可以重新发起对比。

## 15. 使用边界

- 当前没有鉴权和权限控制，只能部署在可信网络。
- Uvicorn 必须使用单 worker。
- 数据规模显著扩大后，应迁移 PostgreSQL、对象存储和独立任务队列。
- 自动备份只覆盖 SQLite 数据库，不包含原始截图；图片需要单独制定存储备份策略。
